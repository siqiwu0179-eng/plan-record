# Plan & Record<br>产品需求文档（PRD）

## 0. 产品概述

Plan & Record 是一个面向个人的轻量规划与生活记录产品。产品最初从 Daily Plan 出发：用户提前写下想做的事情，也可以在事情实际发生后补充记录；随后逐步扩展出长期计划、完成度、旅行和心情等模块。

> 核心表达：Plan what you want to do, record what you actually did.

> 产品愿景：把每一天过好，把长期的事慢慢做完，把值得记住的生活留下来。

> 设计原则：管理是为了帮助完成生活，而不是让“管理生活”本身成为新的任务。

产品以 Daily Plan 为最高频核心，通过 Long-term Plan 支持长期事项推进，通过 Completion 提供阶段反馈，Travel 与 Mood Record 承担轻量生活记录。整体强调低操作成本、即时反馈、自然积累和长期回顾。

## 1. Target User Persona｜目标用户

| 维度 | 定义 |
| --- | --- |
| 核心用户 | 年轻职场人，除工作外还同时处理学习、锻炼、旅行及个人目标。 |
| 行为特征 | 同时推进多个长期目标，希望把事情落实到日常，但不希望使用复杂项目管理工具。 |
| 核心需求 | 希望将每日计划、长期目标、完成反馈、旅行和心情等个人信息集中在一个产品中。 |
| 当前使用条件 | 当前以 Web 为主，更适合日常长时间使用电脑的用户。 |
| 长期范围 | Mobile App 推出后，可扩展至更广泛的个人规划与生活记录用户。 |

当前非核心用户包括团队/企业协作用户、专业项目管理用户，以及完全依赖移动端且很少使用电脑的用户。

## 2. Core User Pain Points｜核心用户痛点

1. 计划工具分散且记录成本高：Calendar 更适合固定时间安排，Notes 容易形成冗长清单，多工具切换增加维护成本。

2. 部分效率工具存在“过度管理”：专注计时、连续打卡、积分等机制可能让管理本身成为额外负担。

3. 长期目标与日常行动容易脱节：同时推进多个目标时，用户容易忘记当前进度、下一步和今天应推进什么。

4. 生活记录分散且难以持续：心情、旅行、摘抄/灵感分布在不同工具中，降低记录和回顾意愿。

5. 已有记录缺少长期反馈价值：完成的任务很快消失，旅行轨迹和心情变化也缺少统一的阶段性回顾。

## 3. Product Goals & Non-goals｜产品目标与边界

### 3.1 Product Goals

| 目标 | 说明 |
| --- | --- |
| G1 降低计划管理成本 | 支持“想到 → 记录 → 分类 → 完成 → 勾选”的轻量流程，不强制设置具体时间或复杂优先级。 |
| G2 支持长期目标推进 | 让长期目标保持清晰 Step 结构，并可与 Daily Plan 建立轻量连接。 |
| G3 形成统一个人空间 | 将 Daily Plan、Long-term Plan、Completion、Travel、Mood Record 集中在同一产品。 |
| G4 提供适度正反馈 | 通过完成度和周期总结提供成就反馈，但不制造连续打卡压力。 |
| G5 增强长期回顾价值 | 让旅行、心情等记录随着使用自然积累并可方便回看。 |

### 3.2 Non-goals

- 不做严格时间管理、专业 Calendar 或复杂日程排程工具。

- 不做 Pomodoro、专注树、连续打卡、积分、排行榜等强游戏化机制。

- 不做复杂任务依赖、多级标签、多层优先级等专业项目管理功能。

- 不做团队协作、企业任务管理或社交功能。

- 不追求“记录生活中的一切”；新增模块必须来自真实且持续的用户需求。

Future Exploration：摘抄 / 灵感，用于快速保存值得回看的句子、摘录和临时想法。阅读笔记暂留 Idea Pool，不进入当前正式 Roadmap。

## 4. Information Architecture｜信息架构

概念上，Plan & Record 可理解为 Plan 与 Record 两类能力；该分组用于解释产品结构，不增加实际导航层级。Web 端采用扁平导航，保证各核心模块可以一键进入。

> Web 全局导航：首页｜每日计划｜长期计划｜完成度｜旅行｜心情

| 一级模块 | 核心内容 | 角色 |
| --- | --- | --- |
| Homepage / Dashboard | 时间、天气、模块摘要、功能入口 | 概览与导航 |
| Daily Plan | 每日任务、固定分类、每日完成度 | 高频执行核心 |
| Long-term Plan | 长期目标、Steps、目标进度 | 长期事项推进 |
| Completion | 周期完成情况、趋势、阶段总结 | 阶段性反馈 |
| Travel | 旅行地点、路线、地图、历史轨迹 | 旅行记录与回顾 |
| Mood Record | 心情记录、日历、趋势、统计 | 情绪记录与回顾 |

Homepage 在 Web 端继续作为默认入口和状态概览页；具体新增、修改、勾选等操作进入对应模块完成。未来所有核心页面增加持久化横向全局导航。

## 5. Module Functional Requirements｜模块功能需求

### 5.1 Homepage / Dashboard

定位：产品概览与统一入口，负责“看 + 进入”，不承担各模块的具体编辑操作。

- 展示时段问候、用户标识、可编辑个人激励语，以及当前时间、日期、星期、天气、温度和地点。

- 展示 Daily Plan、Weekly Completion、Travel、Mood 四张摘要卡，卡片同时作为对应模块入口。

- 展示 Long-term Plan 入口；当前文件夹/浮动式入口后续优化。

- 未来所有 Web 页面统一增加顶部横向全局导航。

### 5.2 Daily Plan

定位：产品最高频的日常执行模块。用户记录当天计划，也可事后补充实际发生但未提前计划的事项。

- 支持日期/周切换、日历选日期和返回本周；顶部展示当周每日完成度。

- 固定四类：学习 / 锻炼 / 饮食 / 其他。支持新增、修改、删除、完成/取消完成。

- 每日完成度 = 当日已完成任务数 ÷ 当日任务总数 × 100%，随任务状态实时更新；所有任务等权。

- 近期：未完成任务可顺延至明天或指定日期，保留原分类；原日期任务继续保留且不自动完成。

- 近期：增加一个轻量“置顶/重要”状态，不改变完成度权重。

- Future：Long-term Step 可加入今天，选择四类之一后生成 Daily Plan 任务。

### 5.3 Long-term Plan

定位：管理需要持续推进的长期事项，帮助用户明确目标进度和下一步。

- 支持多个长期目标；每个目标包含按顺序排列的 Steps。

- 支持 Step 新增、编辑、删除、排序、完成/取消完成。目标完成度 = 已完成 Step 数 ÷ Step 总数。

- 近期：优化当前 Homepage 文件夹/浮动式入口。

- Future：Step → 加入今天 → 选择 Daily Plan 分类；原 Step 继续保留。

- Future：关联 Daily Plan 任务完成/取消完成时同步 Step；关联任务删除后 Step 回到未完成。Step 本身仍可手动切换状态。

### 5.4 Completion

定位：从当前“周完成度”逐步发展为阶段性成就反馈模块。

- 当前展示每日完成度趋势、本周完成统计、已完成/总任务数、最高完成日、计划天数等。

- P0：周期完成度统一为“周期内已完成任务总数 ÷ 周期内任务总数 × 100%”，无任务日期不拉低总体完成度。

- P0：页面独立支持上一周 / 下一周、日期选择和返回本周，不再依赖 Daily Plan 切周。

- Future：扩展周 / 月 / 年完成度，并统一使用上述计算口径。

- Future：新周/月/年首次进入时展示上一周期总结；同一周期只自动展示一次，并支持历史回看。

### 5.5 Travel

定位：轻量记录去过的地方和走过的路线，通过地图与历史数据形成个人旅行轨迹和成就感。

- 记录旅行日期、旅行天数、去过的城市/国家；添加 A 地点 → B 地点的路线并在地图展示。

- 路线不要求区分飞机、火车等交通方式，重点记录“从哪里到哪里”。

- 支持历史路线回顾，并保留飞行距离等已有旅行统计。

- Future：为已有旅行地点/记录添加照片，并可从相应地点查看照片。

### 5.6 Mood Record

定位：以低记录成本留下情绪状态，通过日历和简单统计回顾一段时间的心情变化。

- 支持选择日期（含补记）、心情等级/Emoji、简短文字；支持心情日历、月度统计、趋势和最近记录。

- P0：修复月度统计范围，只统计当前选择月份；日历明确标记已有记录日期。

- 近期：最近记录由 7 条调整为 4 条；通过全局顶部导航直接进入 Mood。

- Future：支持心情照片和 Location。

## 6. Feature Priority｜功能优先级

执行原则：先修正确性和现有体验问题，再完善核心使用链路，最后扩展增强型功能。

| 优先级 | 定义 |
| --- | --- |
| P0 | 当前已有功能存在明显错误，或直接影响核心页面完整可用性，应优先处理。 |
| P1 | 不影响基本使用，但能明显降低操作成本、完善核心链路或加强模块连接。 |
| P2 | 有明确价值但不影响当前核心使用，可在产品更成熟后加入。 |

| 优先级 | 需求 |
| --- | --- |
| P0 | Completion 周期完成度算法修复；Completion 独立切周；Mood 月度统计修复；Mood 日历记录标记。 |
| P1 | Web 顶部全局导航；Long-term 入口优化；Daily Plan 任务顺延；轻量“置顶/重要”；Long-term Step → Daily Plan；关联完成状态同步；Mood 最近记录 7→4。 |
| P2 | Completion 月/年完成度；周/月/年周期总结及历史回看；Travel 照片；Mood 照片与 Location。 |

## 7. User Flow｜用户流程

### 7.1 Overall Flow

用户进入 Plan & Record → Homepage 查看当前状态/选择模块 → 进入 Daily Plan、Long-term Plan、Completion、Travel 或 Mood → 完成对应操作或回顾。未来加入顶部全局导航后，任意核心页面均可直接进入其他模块，无需返回 Homepage 中转。

### 7.2 Core Module Flows

| 模块 | 核心流程 |
| --- | --- |
| Daily Plan | 进入 → 选择日期 → 查看任务 → 新增/编辑/完成 → 系统实时更新完成度；Future：未完成任务 → 顺延 → 选择日期 → 目标日期创建对应任务。 |
| Long-term Plan | 进入 → 选择目标 → 查看/调整 Steps → 完成 Step → 更新目标进度；Future：Step → 加入今天 → 选择分类 → Daily Plan。 |
| Completion | 进入 → 查看当前周期趋势与统计 → 切换周期 → 查看对应数据；Future：周/月/年切换及周期总结。 |
| Travel | 进入 → 查看地图/历史 → 添加起点和终点 → 保存 → 地图及统计更新；Future：已有地点/记录 → 添加/查看照片。 |
| Mood | 进入 → 选择日期 → 选择心情 → 输入简短文字 → 保存 → 日历/统计/最近记录更新。 |

### 7.3 Key Cross-module Flow

> Long-term Plan Step → Daily Plan Task → Completion

长期目标明确下一步 → Step 加入今天 → 在 Daily Plan 执行 → 完成状态反馈至长期目标 → 任务数据进入周期完成统计。Travel 与 Mood 当前保持相对独立，以轻量记录和历史回顾为主。

## 8. Page & Interaction Requirements｜页面与交互要求

### 8.1 Global Interaction

- 所有 Web 核心页面使用统一顶部横向导航：首页｜每日计划｜长期计划｜完成度｜旅行｜心情；当前页面有明确选中状态。

- 模块切换尽量一步完成，不增加 Plan/Record 二级菜单。

- Homepage 保持概览和入口定位，不发展为复杂操作面板。

- 新增功能优先复用现有视觉语言和组件，避免不同模块形成割裂体验。

### 8.2 Module-specific Interaction

| 模块 | 关键交互要求 |
| --- | --- |
| Daily Plan | 勾选/取消勾选后立即反馈并重算完成度；顺延时选择目标日期，原任务不被移动或删除。 |
| Long-term Plan | Step 加入今天时先选择 Daily Plan 分类，再生成任务；关联状态变化应有一致反馈。 |
| Completion | 周期切换控件与当前周期信息保持邻近；提供明确“返回本周”。 |
| Travel | 添加路线保持轻量，以起点和终点为核心输入。 |
| Mood | 记录流程保持简短；日历中的已记录日期必须清晰可识别。 |

### 8.3 Interaction Principles

- 低操作成本：常用操作减少点击和非必要填写。

- 即时反馈：保存、勾选、删除、状态切换后立即反映结果。

- 一致性：相似操作在不同模块保持相同逻辑。

- 渐进式复杂度：照片、Location 等增强信息不作为强制字段。

- 可回退：完成/取消完成等状态操作尽量可逆。

- 避免过度打扰：周期总结等主动反馈控制出现频率。

## 9. Data & State Rules｜数据与状态规则

本部分定义会直接影响产品行为的核心状态规则；数据库字段和具体表结构由技术实现另行设计。

| 对象 | 核心规则 |
| --- | --- |
| Daily Task | 任务属于具体日期和固定分类；完成状态可切换；新增/删除/完成状态变化均触发当日完成度实时重算。 |
| Task Carry-over | 顺延在目标日期创建对应任务，保留分类；原日期任务继续存在且保持原状态。 |
| Long-term Step | Step 属于长期目标，可独立完成/取消完成；目标完成度按 Step 等权计算。 |
| Linked Step / Task | 关联任务完成时 Step 完成；取消完成时 Step 未完成；关联任务删除时 Step 回到未完成。复杂多关联情况后续实现前再确认。 |
| Completion | 日/周/月/年均采用“周期已完成任务总数 ÷ 周期任务总数”；无任务日期不参与总体完成度分母。 |
| Mood | 记录与用户选择的日期绑定，月度统计只读取当前选择月份。 |
| Travel | 路线以起点—终点为核心记录，不依赖交通方式分类。 |

数据存储层需要进一步检查现有 Supabase 读写、同步、错误处理及各模块数据结构，作为后续工程优化任务。

## 10. Edge & Error Cases｜边界与异常场景

| 场景 | 预期处理 |
| --- | --- |
| 周期内无任何任务 | 完成度显示为无任务/无可计算数据，不将该周期误解释为 0% 完成。具体展示文案在 UI 实现时确定。 |
| 删除/取消完成任务 | 相关完成度立即重新计算；关联 Long-term Step 按同步规则更新。 |
| 顺延任务失败 | 原日期任务必须保留，避免因创建未来任务失败导致原数据丢失。 |
| 保存失败/网络异常 | 不得静默覆盖用户输入；应提示失败并允许重试。 |
| Mood 月份无记录 | 展示空状态，不生成虚假统计。 |
| Travel 路线信息不足 | 不保存不完整路线，并提示补充起点/终点。 |
| 跨页面数据更新 | 返回相关模块时应显示最新状态，避免旧缓存覆盖新数据。 |

## 11. Success Metrics｜成功指标

当前产品处于个人真实使用和产品能力验证阶段，尚无规模化用户，因此不设置虚假的 DAU、留存率或商业 KPI。现阶段指标用于验证核心流程是否真正降低记录与执行成本。

| 指标 | 定义/观察方式 | 当前用途 |
| --- | --- | --- |
| 任务完成率 | 周期内完成任务数 ÷ 周期任务总数 | 验证 Daily Plan 与 Completion 是否能形成有效执行反馈。 |
| 计划使用频率 | 有任务记录的日期数 / 使用周期 | 观察 Daily Plan 是否持续成为高频核心。 |
| 任务顺延使用情况 | 顺延任务数量及后续完成情况 | 验证顺延功能是否解决未完成任务处理问题。 |
| Long-term → Daily 转化 | 由 Step 加入 Daily Plan 的任务数量/完成情况 | 验证长期目标与日常执行连接是否有实际价值。 |
| 模块使用分布 | Daily / Long-term / Completion / Travel / Mood 的进入和操作次数 | 识别真正高频模块与低频但有回顾价值的模块。 |
| 错误/保存失败 | 关键写入失败、同步异常、重复/丢失数据情况 | 优先保障数据可靠性。 |

在只有单一真实用户的阶段，指标主要用于纵向观察和功能验证，不用于对外宣称规模化产品表现。

## 12. Tracking & Metrics System｜埋点与分析

在核心功能稳定后补充轻量事件追踪。目标不是建立复杂增长体系，而是让后续产品决策可以基于真实行为数据。

| 事件类别 | 建议记录 |
| --- | --- |
| Daily Plan | task\_created、task\_completed、task\_uncompleted、task\_deleted、task\_carried\_over |
| Long-term | goal\_created、step\_created、step\_completed、step\_added\_to\_daily |
| Completion | completion\_viewed、period\_switched、period\_summary\_viewed |
| Travel | travel\_viewed、route\_created、photo\_added（Future） |
| Mood | mood\_created、mood\_viewed、month\_switched、photo/location\_added（Future） |
| Navigation | module\_viewed / global\_nav\_clicked |

- 优先使用 Supabase 中真实业务数据 + 必要事件表进行 SQL 分析。

- 建立简单 Dashboard，展示任务完成、模块使用、长期目标转化等关键指标。

- 埋点字段保持最小化，避免为了分析而增加不必要的数据采集。

## 13. Non-functional Requirements｜非功能需求

| 类别 | 要求 |
| --- | --- |
| 数据可靠性 | 用户保存、完成、删除、顺延等关键操作不得出现静默丢失；数据库写入失败需可感知。 |
| 一致性 | 同一数据在不同页面显示一致；关联 Step / Task 状态不得长期不同步。 |
| 性能 | 常用页面和任务操作应保持即时响应感；避免因统计或地图加载阻塞核心计划操作。 |
| 安全与隐私 | 个人计划、心情、旅行等数据仅对登录用户可见；密钥和环境变量不得暴露在前端仓库。 |
| 兼容性 | 当前优先保证主流桌面浏览器的 Web 使用体验；Mobile App 后续单独设计。 |
| 可维护性 | 新增模块保持清晰数据边界；避免多个模块共享单条不可维护的数据结构。 |
| 可恢复性 | 关键写入失败时保留用户输入或提供重试路径，避免用户重新录入。 |

## 14. MVP & Version Evolution｜MVP与版本演进

| 版本 | 核心内容 | 阶段目标 |
| --- | --- | --- |
| V1 / MVP | Daily Plan + 周完成度；固定分类；浏览器本地存储；基础 Web 部署 | 验证“轻量每日计划 + 完成反馈”是否满足真实使用需求。 |
| V2 | Homepage、Travel、Mood；Supabase 数据库；登录；整体 UI/背景优化 | 从单一计划工具扩展为个人规划与生活记录空间。 |
| V2.x / 当前阶段 | Long-term Plan；持续真实使用；开始修复数据、导航和跨模块体验问题 | 完善核心链路并提高产品稳定性。 |
| V2.x / 近期 | P0 修复；全局导航；任务顺延；Long-term 与 Daily 连接；轻量重要状态 | 先把现有产品做正确、做顺。 |
| V3 / 中期 | 埋点与 SQL 分析；周/月/年反馈；周期总结；Travel/Mood 增强 | 建立数据驱动迭代与更完整的回顾体验。 |
| V4 / 长期 | 独立 Mobile App；移动端 IA；锁屏快速查看/记录；Web/App 同步 | 扩展使用场景，同时保持低操作成本。 |
